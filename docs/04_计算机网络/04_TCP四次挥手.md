## 二、 具体考察内容

### 1. 核心定义及全双工释放原理

#### 1.1 全双工通信及半关闭机制
TCP 协议提供全双工（Full-Duplex）可靠字节流服务。这意味着在一个已建立的 TCP 连接中，存在两条完全独立、方向相反的逻辑传输信道：
- **信道 A $\to$ B**：主机 A 发送数据，主机 B 接收并确认。
- **信道 B $\to$ A**：主机 B 发送数据，主机 A 接收并确认。

因此，TCP 连接的释放必须是对称且相互独立的。终止一个方向的数据流并不会自动关闭另一个方向的数据流：
- 当一端发送 `FIN` 报文段时，仅表明该端**已经没有应用层数据需要发送**，请求关闭己方的发送信道。
- 此时该端依然具备接收数据的能力，另一端仍可继续发送未传输完毕的数据。这种单向关闭、单向维持连接的状态被称为**半关闭（Half-Close）**。

#### 1.2 为什么连接释放通常需要“四次挥手”而非“三次”？
在 TCP 连接建立阶段，服务端的 `SYN`（同步自身初始序号）和对客户端的 `ACK`（确认客户端初始序号）可以合并在同一个报文段（`SYN+ACK`）中发送，因而仅需三次握手。

而在连接释放阶段：
1. 当主动关闭方发出 `FIN` 报文段时，被动关闭方收到后必须立即回复 `ACK`，确认主动方的释放请求。
2. 此时，被动关闭方的应用层可能仍有缓冲区数据尚未发送完毕（例如服务器正在向客户端回传大文件的剩余部分）。因此，被动关闭方不能立即向主动方发送 `FIN`。
3. 直到被动关闭方的应用层处理完毕、所有残留数据发送完毕并显式调用 `close()` 关闭套接字时，被动关闭方才会独立发出己方的 `FIN` 报文段。
4. 主动关闭方再针对该 `FIN` 回复 `ACK`。

正因为被动关闭方的“对前向关闭的确认（`ACK`）”以及“己方向后关闭的请求（`FIN`）”在绝大多数现实场景中存在时间差，二者无法合并发送，故完整的连接拆除通常需要四次报文段交互，即四次挥手。

> **特殊场景（三次挥手）**：若被动关闭方在收到主动方的 `FIN` 时恰好没有残留数据需要发送，且应用进程紧接着执行了关闭操作，TCP 协议栈允许将第二次挥手的 `ACK` 和第三次挥手的 `FIN` 合并为一个报文段发送（即标志位同时置位 `FIN=1, ACK=1`）。此时四次挥手退化为三次挥手（如 2022 年第 39 题求解最小关闭时间模型即基于此边界推导）。

### 2. 报文段首部控制位及序号同步规则

#### 2.1 涉及的核心控制位
TCP 报文段首部包含 6 个核心标志位（Flags），在释放阶段关键作用的有两个：
- **FIN（Finish）**：释放连接控制位。当 $\text{FIN} = 1$ 时，表明此报文段发送方的数据已发送完毕，请求释放传输信道。
- **ACK（Acknowledgment）**：确认控制位。当 $\text{ACK} = 1$$ \text{时，报文段首部的 32 位确认序号（Acknowledgment Number）字段有效。在 TCP 连接建立后的所有正常交互报文段中，} $$\text{ACK}$ 位均必须置 1。

#### 2.2 序号消耗判定定理及数学推导
在 408 考研计算中，报文段是否占用序号空间是命题人设置计算陷阱的最高频手段。必须严格遵循以下判定准则：

1. **准则一（SYN 消耗性）**：连接建立时，$\text{SYN} = 1$ 的报文段即便不携带任何应用层数据（即数据载荷长度为 0），也必须**占用 1 个序号**。
2. **准则二（FIN 消耗性）**：连接释放时，$\text{FIN} = 1$ 的报文段即便不携带任何应用层数据，也必须**占用 1 个序号**。
3. **准则三（纯 ACK 零消耗）**：不携带数据且不含 SYN/FIN 标志的纯 ACK 报文段，**不消耗序号**。其发送时的序列号字段保持为当前待发送字节序号，但不使发送端的序列号指针发生自增。
4. **准则四（载荷及标志位叠加）**：若报文段包含 $L$ 字节的应用层数据，同时携带 FIN 标志，则该报文段占用的序号空间总数为：
   $$\Delta \text{seq} = L + 1$$

#### 2.3 序号演变数学模型
假设主动关闭方 A 的初始序号为 $\text{ISN}_A$$ \text{，在连接生命周期内共向被动方 B 成功发送了} $$N$ 字节应用层数据（无乱序重传）：
1. 握手阶段：A 发送 `SYN=1, seq = ISN_A`，占用序号 $\text{ISN}_A$。
2. 数据阶段：A 发送的首字节数据序号为：
   $$\text{seq}_{\text{first}} = \text{ISN}_A + 1$$
   A 发送的尾字节数据序号为：
   $$\text{seq}_{\text{last}} = \text{seq}_{\text{first}} + N - 1 = \text{ISN}_A + N$$
3. 挥手阶段：A 发送的释放请求报文段（第一次挥手）序号紧接在尾字节之后：
   $$\text{seq}_{\text{FIN}} = \text{seq}_{\text{last}} + 1 = \text{ISN}_A + N + 1$$
4. 确认阶段：B 收到 A 的 FIN 报文段后，回复第二次挥手确认报文段，其确认号为：
   $$\text{ack}_B = \text{seq}_{\text{FIN}} + 1 = \text{ISN}_A + N + 2$$

上述公式构成了推导 2020 年第 39 题及 2023 年第 47 题的标准数学解析依据。

### 3. 连接释放有限状态自动机（FSM）全流程

TCP 四次挥手过程涉及两端各自主机内部复杂的传输控制块（TCB）状态机跃迁。各状态定义及演进逻辑如下：

```text
       主动关闭方 (Active Closer)                        被动关闭方 (Passive Closer)
          [ESTABLISHED]                                      [ESTABLISHED]
                |                                                  |
                | (应用层调用close, 发送FIN)                       |
                |------------------ [1] FIN=1, seq=u ------------->| (收到FIN, 回复ACK)
         [FIN_WAIT_1]                                              |
                |                                            [CLOSE_WAIT] (半关闭状态)
                |<----------------- [2] ACK=1, ack=u+1, seq=v -----|
         [FIN_WAIT_2]                                              | (应用层发送残留数据)
                |                                                  | (数据发完, 调用close)
                |                                                  | 发送FIN+ACK
                |<----------------- [3] FIN=1, ACK=1, seq=w, ack=u+1
          [TIME_WAIT]                                        [LAST_ACK]
                | (发送ACK, 启动2MSL计时器)                        |
                |------------------ [4] ACK=1, ack=w+1, seq=u+1 -->| (收到ACK, 彻底关闭)
                |                                               [CLOSED]
        (等待 2MSL 超时)
                |
             [CLOSED]
```

#### 3.1 状态转移微观分解

##### 第一次挥手：主动关闭方发起释放请求
- **动作**：主机 A 的应用进程调用关闭操作，向主机 B 发送连接释放报文段，首部控制位 $\text{FIN} = 1$$ \text{，序列号} $$\text{seq} = u$（$u$ 等于 A 前面已传送数据的最后一个字节序号加 1）。
- **状态转移**：主机 A 从 `ESTABLISHED`（连接建立）状态转入 **`FIN_WAIT_1`**（终止等待 1）状态。此时 A 停止向 B 发送应用层数据。

##### 第二次挥手：被动关闭方确认半关闭
- **动作**：主机 B 收到连接释放报文段后，立即发出确认报文段，首部控制位 $\text{ACK} = 1$$ \text{，确认号} $$\text{ack} = u + 1$$ \text{，自身序号} $$\text{seq} = v$。
- **状态转移**：
  - 主机 B 从 `ESTABLISHED` 状态转入 **`CLOSE_WAIT`**（关闭等待）状态。此时 TCP 连接处于半关闭状态，B 到 A 的反向信道仍然可用。
  - 主机 A 收到该确认报文段后，状态从 `FIN_WAIT_1` 转入 **`FIN_WAIT_2`**（终止等待 2）状态，等待 B 发送己方的连接释放报文段。

##### 第三次挥手：被动关闭方发起完全释放
- **动作**：若主机 B 已经没有向 A 发送的数据，其应用进程调用关闭操作，向 A 发送连接释放报文段，首部控制位 $\text{FIN} = 1, \text{ACK} = 1$$ \text{，序列号} $$\text{seq} = w$$ \text{（在半关闭状态下 B 可能又发送了部分数据），确认号重复上一次的} $$\text{ack} = u + 1$。
- **状态转移**：主机 B 从 `CLOSE_WAIT` 状态转入 **`LAST_ACK`**（最后确认）状态，等待 A 的最终确认。

##### 第四次挥手：主动关闭方确认及转入时间等待
- **动作**：主机 A 收到 B 的连接释放报文段后，必须对此发出确认，首部控制位 $\text{ACK} = 1$$ \text{，确认号} $$\text{ack} = w + 1$$ \text{，序号为} $$\text{seq} = u + 1$。
- **状态转移**：
  - 主机 A 从 `FIN_WAIT_2` 状态转入 **`TIME_WAIT`**（时间等待）状态。**此时 TCP 连接尚未释放**，A 必须在此状态下启动时间等待计时器，维持等待时间为 **$2\text{MSL}$**（两倍最长报文段寿命）。当计时器超时后，A 方才转入 **`CLOSED`**（连接关闭）状态，撤销 TCB 控制块。
  - 主机 B 收到 A 发送的确认报文段后，无需等待任何计时器，立即从 `LAST_ACK` 状态转入 **`CLOSED`** 状态，撤销 TCB 控制块。

#### 3.2 特殊状态机分支：双方同时主动关闭（CLOSING 状态）
若主机 A 和主机 B 同时向对端发送 `FIN` 报文段：
1. 双方均从 `ESTABLISHED` 状态转入 **`FIN_WAIT_1`** 状态。
2. 双方在 `FIN_WAIT_1` 状态下均未收到预期的 `ACK`，而是收到了对端的 `FIN` 报文段。
3. 双方各自回复 `ACK` 报文段，此时双方状态机均转移至 **`CLOSING`** 状态。
4. 随后双方收到对端对己方 `FIN` 的 `ACK` 后，状态机由 `CLOSING` 转入 **`TIME_WAIT`** 状态。
5. 最终等待 $2\text{MSL}$ 超时后进入 `CLOSED` 状态。

### 4. TIME_WAIT 状态及 2MSL 机制深度剖析

#### 4.1 MSL 严格定义及物理内涵
**MSL（Maximum Segment Lifetime，最长报文段寿命）**是任何 TCP 报文段在互联网中能够存活的最长时间。
- **物理成因**：IP 协议首部包含 8 位的生存时间（Time To Live, TTL）字段，路由器每转发一次数据报将 TTL 减 1，TTL 归零则丢弃该数据报并向源端发送 ICMP 超时差错报文。MSL 即为 TTL 在实际互联网拓扑中耗尽的最大时间上限工程估计。
- **标准约定**：RFC 793 推荐 MSL 设为 2 分钟（120 秒）。在现代高速网络工程实践中，操作系统通常采用更激进的经验值，例如 Linux 默认将 MSL 设定为 30 秒或 60 秒。408 考研计算中若无特别说明，严格代入题干给定的 MSL 数值。

#### 4.2 为什么必须在 TIME_WAIT 状态等待 2MSL？（两大约束原因）

这是 408 考研及复试面试中极高频的经典理论大题考点。设置 $2\text{MSL}$ 等待时间有两大不可替代的根本约束：

##### 约束一：保证全双工连接可靠终止（保证被动关闭方能够收到最后的 ACK 报文段）
- **失效场景推演**：假设主机 A 发送的第四次挥手确认报文段（$\text{ACK} = 1$）在网络传输中丢失。
- **超时重传机制**：主机 B 在 `LAST_ACK` 状态下启动的超时重传定时器（RTO）发生超时。B 将重传第三次挥手的报文段（$\text{FIN} = 1, \text{ACK} = 1$）。
- **保护效果**：
  - 若主机 A 不经过 `TIME_WAIT` 等待，而是在发送第四次挥手 ACK 后直接进入 `CLOSED` 状态，则 A 的所有连接资源已释放。当收到 B 重传的 FIN 时，A 只能回复**复位报文段（RST）**，导致主机 B 发生连接异常终止（Connection Reset by Peer），无法优雅地完成正常关闭。
  - 若主机 A 维持 `TIME_WAIT` 状态：A 能在 2MSL 窗口内接收到重传的 FIN 报文段，并重新向 B 发送 ACK，同时**重启 2MSL 计时器**。这使得 B 能够顺利转入 `CLOSED` 状态。
- **时间预算（2MSL 的构成）**：
  $$ \text{第四次挥手 ACK 达到对端的最长时间 (1 MSL)} + \text{对端重传 FIN 返还本端的最长时间 (1 MSL)} = 2\text{MSL} $$

##### 约束二：净化网络环境，防止“已失效的旧报文段”出现在后续新连接中
- **四元组复用冲突**：TCP 连接由四元组（源 IP、源端口、目的 IP、目的端口）唯一标识。若主机 A 在断开连接后立即进入 `CLOSED` 状态并释放端口，上层应用可能迅速使用相同的四元组建立一个全新的 TCP 连接（称为新化身，New Incarnation）。
- **幽灵数据污染**：由于网络路由器队列拥塞导致延迟，上一代旧连接中滞留的某些旧报文段可能在新连接建立后才迟迟抵达目的主机。若新连接此时恰好落入接收窗口范围内，该迟到旧报文将被新连接错误接收为有效数据，造成严重的字节流数据混乱。
- **保护效果**：A 在 `TIME_WAIT` 状态停留持续 $2\text{MSL}$ 时间，能够确保本连接持续时间内所产生的所有报文段均在网络中因超过 TTL 寿命而**彻底消亡**。当后续重新复用该四元组建立新连接时，网络中绝不会出现任何旧连接的残留滞留报文。

#### 4.3 TIME_WAIT 系统影响及工程调优

在互联网服务端高并发场景中，TIME_WAIT 状态是一把双刃剑：
1. **系统影响**：
   - **套接字资源消耗**：每个 TIME_WAIT 状态的套接字均需在操作系统内核维持传输控制块（TCB）及文件描述符，消耗内存。
   - **端口耗尽危机**：若由服务端主动发起连接关闭，在短连接极高并发下，服务端会产生数以万计的 TIME_WAIT 连接，导致可用临时端口（Ephemeral Ports）迅速耗尽，后续对其他服务的调用将因无法分配端口而抛出 `Cannot assign requested address` 异常。
2. **工程解决方案**：
   - **优化架构设计**：尽可能让客户端发起主动关闭，将 TIME_WAIT 状态的等待成本转嫁至海量的客户端分布承担。
   - **应用层长连接**：在 HTTP 协议中使用 `Keep-Alive` 复用 TCP 物理连接，减少频繁的四次挥手握手开销。
   - **套接字重用**：在套接字编程中设置 `SO_REUSEADDR` 选项，允许处于 TIME_WAIT 状态的地址/端口直接被新套接字绑定。
   - **内核快速复用**：在启用了 TCP 时间戳选项（RFC 1323）的前提下，通过内核参数（如 `tcp_tw_reuse`）在收到时间戳递增的安全 SYN 报文时，安全复用处于 TIME_WAIT 状态的连接元组。

#### 4.4 为什么被动关闭方不需要维持 TIME_WAIT 状态？
被动关闭方在 `LAST_ACK` 状态下发出 FIN 后，只要收到主动关闭方回传的最终 ACK，就证明主动方已经正确处理了释放流程。若该 ACK 丢失，被动关闭方可以通过重传 FIN 重新驱动流程。一旦收到 ACK，其连接使命已经完成，直接转入 CLOSED 即可；而网络中可能残留的旧数据包，将由主动关闭方所持有的 $2\text{MSL}$ 计时器在全局上完成网络清空，被动方无需重复占用资源等待。

### 5. 易混淆概念深度辨析

#### 5.1 三次握手和四次挥手特性对比

```text
+----------------------+------------------------------------+------------------------------------+
| 比较维度             | TCP 三次握手                       | TCP 四次挥手                       |
+----------------------+------------------------------------+------------------------------------+
| 核心目标             | 同步初始序列号（ISN）、协商通信参数| 对称拆除全双工传输信道             |
| 报文交互次数         | 3 次                               | 4 次（无数据发送时可合并为 3 次）  |
| 控制位标志           | 第一次: SYN=1                      | 第一次: FIN=1                      |
|                      | 第二次: SYN=1, ACK=1               | 第二次: ACK=1                      |
|                      | 第三次: ACK=1                      | 第三次: FIN=1, ACK=1               |
|                      |                                    | 第四次: ACK=1                      |
| 控制位序号消耗       | SYN 报文段消耗 1 个序号            | FIN 报文段消耗 1 个序号            |
| 纯 ACK 序号消耗      | 均不消耗序号                       | 均不消耗序号                       |
| 核心等待计时器       | 无长时间等待，发完第三次握手即就绪 | 存在 2MSL 等待计时器（TIME_WAIT）  |
| 触发主体             | 仅客户端主动发起                   | 客户端或服务端均可主动发起         |
+----------------------+------------------------------------+------------------------------------+
```

#### 5.2 正常 FIN 释放及异常 RST 终止对比

```text
+----------------------+------------------------------------+------------------------------------+
| 比较维度             | 正常 FIN 释放（四次挥手）          | 异常 RST 终止（连接重置）          |
+----------------------+------------------------------------+------------------------------------+
| 控制位               | FIN=1, ACK=1                       | RST=1                              |
| 关闭模式             | 优雅关闭（Graceful Close）         | 暴力异常中止（Abrupt Close）       |
| 缓冲区数据处理       | 保证已排队缓冲区数据可靠传达对端   | 丢弃发送/接收缓冲区中的全部排队数据|
| 交互流程             | 经历四次挥手交互及 TIME_WAIT 等待  | 单向发送单个 RST 段，无需对方确认  |
| 典型触发场景         | 应用层正常调用 close()             | 访问未监听端口、进程异常崩溃崩溃、 |
|                      |                                    | 穿越防火墙阻断、半打开连接检测     |
+----------------------+------------------------------------+------------------------------------+
```

#### 5.3 CLOSE_WAIT 和 TIME_WAIT 状态差异及排障定位

- **`CLOSE_WAIT`（出现在被动关闭方）**：
  - **产生原因**：已收到对端的 FIN 并回复了 ACK，正在等待本地应用进程调用 `close()`。
  - **故障特征**：若服务端系统监控中出现海量 `CLOSE_WAIT` 连接，属于**应用程序代码 Bug**（例如业务逻辑死锁、线程池满载导致没有及时执行套接字的 `socket.close()` 释放操作）。
- **`TIME_WAIT`（出现在主动关闭方）**：
  - **产生原因**：已发送最终的 ACK，按照协议规范等待 $2\text{MSL}$ 净化网络。
  - **故障特征**：若系统监控中出现海量 `TIME_WAIT` 连接，通常属于**高并发短连接业务架构设计使然**（如 HTTP 客户端高频请求或 Nginx 反向代理未配置连接池），需通过架构改造（长连接）或内核调优解决。

### 2024 年第 38 题

#### 题目题干
假设主机 H 通过 TCP 向服务器发送长度为 3000B 的报文，往返时间 $\text{RTT} = 10\text{ ms}$$ \text{，最长报文段寿命} $$\text{MSL} = 30\text{ s}$$ \text{，最大报文段长度} $$\text{MSS} = 1000\text{ B}$，忽略 TCP 段的传输时延，报文传输结束后 H 首先请求断开连接，则从 H 请求建立 TCP 连接时刻起，到 H 进入 CLOSED 状态为止，所需时间至少是（ ）。

#### 选项设置
A. 30.03 s  
B. 30.04 s  
C. 60.03 s  
D. 60.04 s  

#### 考查知识点
1. TCP 三次握手建立连接的时间开销（$1\text{ RTT}$）。
2. TCP 慢开始算法在传输 3000B 数据时的轮次及耗时推导（$2\text{ RTT}$）。
3. TCP 四次挥手释放连接的最短时延（$1\text{ RTT}$$ \text{）以及主动关闭方在 TIME_WAIT 状态必须停留的} $$2\text{MSL}$ 时间。

#### 逐步深度推导解析
整个通信生命周期严格划分为连接建立、数据传输和连接释放三个阶段。

##### 阶段一：建立 TCP 连接（三次握手）
- 主机 H 向服务器发送 `SYN` 报文段（历经单向传播时延 $0.5\text{ RTT}$）。
- 服务器收到后回复 `SYN+ACK` 报文段（历经单向传播时延 $0.5\text{ RTT}$）。
- 主机 H 收到该确认后，连接正式建立。此过程用时为：
  $$T_{\text{conn}} = 0.5\text{ RTT} + 0.5\text{ RTT} = 1\text{ RTT}$$
- 按照 TCP 规范，主机 H 发送的第三次握手 `ACK` 报文段可以携带应用层数据，或者在发出 `ACK` 后立即发送第一个数据段，因此数据传输从此时刻立即开始。

##### 阶段二：传输 3000B 数据（慢开始机制）
- 已知 $\text{MSS} = 1000\text{ B}$$ \text{，需发送的数据总量为} $$3000\text{ B} = 3\text{ MSS}$。
- TCP 连接刚建立时，拥塞窗口初始值 $\text{cwnd} = 1\text{ MSS}$：
  - **第 1 轮数据传输**：H 发送第 1 个数据段（$1000\text{ B}$$ \text{）。经过} $$1\text{ RTT}$$ \text{后，H 收到服务器对该段的确认 ACK。此时累计发送并确认} $$1000\text{ B}$$ \text{。根据慢开始算法，拥塞窗口翻倍为} $$\text{cwnd} = 2\text{ MSS}$$ \text{。用时} $$1\text{ RTT}$。
  - **第 2 轮数据传输**：H 连续发送剩余的 2 个数据段（共 $2000\text{ B}$$ \text{）。经过} $$1\text{ RTT}$$ \text{后，H 收到服务器对这} $$2000\text{ B}$$ \text{数据的确认 ACK。此时} $$3000\text{ B}$$ \text{数据全部传输完成并确认。用时} $$1\text{ RTT}$。
- 数据传输阶段总耗时为：
  $$T_{\text{data}} = 1\text{ RTT} + 1\text{ RTT} = 2\text{ RTT}$$

##### 阶段三：断开 TCP 连接（四次挥手及 TIME_WAIT）
- 题干要求“所需时间至少是”，即寻找最快释放路径：
  - 主机 H 确认数据传输完毕后，立即发送第一次挥手 `FIN` 报文段。经过 $0.5\text{ RTT}$ 到达服务器。
  - 服务器此时已经没有数据需要发送，在最理想情况下，服务器立即回复 `ACK` 并同时发送自己的 `FIN` 报文段（即将第二次和第三次挥手合并发送或零间隔连续发出）。经过 $0.5\text{ RTT}$ 到达主机 H。
  - 从 H 发送 `FIN` 到收到服务器的 `FIN`，共耗时 $0.5\text{ RTT} + 0.5\text{ RTT} = 1\text{ RTT}$。
  - H 收到服务器的 `FIN` 后，立即发出第四次挥手 `ACK` 报文段，**同时主机 H 状态转移至 TIME_WAIT**。
- 主机 H 在 TIME_WAIT 状态下，必须强制等待 $2\text{MSL}$ 计时器超时后，才能转入 CLOSED 状态。
- 因此，连接释放阶段主机 H 从发起断开到进入 CLOSED 状态所需的最少时间为：
  $$T_{\text{close}} = 1\text{ RTT} + 2\text{MSL}$$

##### 汇总全流程时间下界
$$T_{\text{total}} = T_{\text{conn}} + T_{\text{data}} + T_{\text{close}} = 1\text{ RTT} + 2\text{ RTT} + (1\text{ RTT} + 2\text{MSL}) = 4\text{ RTT} + 2\text{MSL}$$

代入已知参数 $\text{RTT} = 10\text{ ms} = 0.01\text{ s}$，$\text{MSL} = 30\text{ s}$：
$$T_{\text{total}} = 4 \times 0.01\text{ s} + 2 \times 30\text{ s} = 0.04\text{ s} + 60\text{ s} = 60.04\text{ s}$$

#### 正确答案
**D**

### 2023 年第 47 题

#### 题目题干
如图，主机 H 登录到 FTP 服务器后，向服务器上传一个大小为 18000B 的文件 F，假设 H 传输 F 建立数据连接时，选择的初始序号为 100，MSS = 1000B，拥塞控制的初始阈值是 4MSS，RTT = 10ms，忽略 TCP 的传输时延，在 F 的传送过程中，H 以 MSS 段向服务器发送数据，且始终没有错误、丢包和乱序。

```text
  +----------+               +--------+               +----------------+
  |  主机 H  | <===========> | 路由器 | <===========> |   FTP 服务器   |
  +----------+               +--------+               +----------------+
```

(1) FTP 的控制连接是持久的还是非持久的？FTP 的数据连接是持久的还是非持久的？H 登录服务器时，建立的 FTP 连接是数据连接还是控制连接？  
(2) H 通过数据连接发送 F 时，F 的第一个字节序号是多少？在断开数据连接的过程中，FTP 发送的第二次挥手的 ACK 序号是多少？  
(3) F 发送过程中，当 H 收到确认序号为 2101 的确认时，H 的拥塞窗口调整为多少？收到确认序号为 7101 的确认段时，H 的拥塞窗口调整为多少？  
(4) H 从请求建立数据连接开始，到确认 F 已被服务器全部接收为止，至少要多长时间？期间应用层数据平均发送速率是多少？

#### 考查知识点
1. FTP 协议的双连接体系（控制连接持久，数据连接非持久）。
2. TCP SYN 和 FIN 报文段对序列号空间的消耗规则（各占 1 个序号）。
3. 拥塞控制慢开始及拥塞避免算法中拥塞窗口（cwnd）的更新机制。
4. 基于 RTT 轮次的时延推导及应用层平均吞吐量计算。

#### 逐步深度推导解析

##### 第 (1) 问解析
- **FTP 协议机制**：FTP 采用分离的双连接架构。
  - **控制连接**：用于传输控制命令和应答（如用户名、密码、文件操作命令等）。控制连接在客户端和服务端整个会话期间一直保持打开，因此是**持久的（Persistent）**。
  - **数据连接**：专用于传输文件内容或目录列表。每次有文件上传或下载时才临时建立，数据传输完毕后立即关闭，因此是**非持久的（Non-persistent）**。
- **登录过程**：用户执行登录鉴权，交互身份凭据及会话指令，因此建立的是**控制连接**。

##### 第 (2) 问解析
- **首字节序号推导**：
  - 建立数据连接时，主机 H 发送的 `SYN` 段选择的初始序号 $\text{ISN} = 100$。
  - 根据准则一，`SYN` 报文段不携带数据但必须消耗 1 个序号。
  - 因此，数据传输的起始序号为：
    $$\text{seq}_{\text{first}} = \text{ISN} + 1 = 100 + 1 = 101$$
- **第二次挥手 ACK 确认序号推导**：
  - 文件 $F$$ \text{的大小为} $$18000\text{ B}$。
  - 文件所有字节占用的序号区间为 $[101, 101 + 18000 - 1] = [101, 18100]$。
  - 文件发送完毕后，主机 H 主动发起连接释放，发出第一次挥手 `FIN` 报文段。
  - 该 `FIN` 报文段的序号必须紧接在数据尾字节之后：
    $$\text{seq}_{\text{FIN}} = 18100 + 1 = 18101$$
  - 根据准则二，`FIN` 报文段即便不携带应用层数据，也必须消耗 1 个序号。
  - 服务器收到后回复第二次挥手 `ACK` 报文段，其确认序号是对该 FIN 序号的确认，应为：
    $$\text{ack} = \text{seq}_{\text{FIN}} + 1 = 18101 + 1 = 18102$$

##### 第 (3) 问解析
- **初始状态**：$\text{cwnd} = 1\text{ MSS} = 1000\text{ B}$$ \text{，门限} $$\text{ssthresh} = 4\text{ MSS} = 4000\text{ B}$。
- **轮次推导**：
  - **第 1 轮（慢开始）**：H 发送 1 个 MSS（字节范围 $101 \sim 1100$$ \text{）。收到确认序号为 1101 的 ACK 时，确认了 1 个新段，} $$\text{cwnd}$$ \text{增加 1 MSS 变为} $$2\text{ MSS}$。
  - **第 2 轮（慢开始）**：H 连续发送 2 个 MSS（字节范围 $1101 \sim 2100$$ \text{及} $$2101 \sim 3100$）。
    - 当 H 收到确认序号为 2101 的 ACK 时，表示第 1 个 MSS（$1101 \sim 2100$）已被确认。根据慢开始算法，每收到一个对新报文段的确认，拥塞窗口增加 1 MSS。因此此时拥塞窗口调整为：
      $$ \text{cwnd} = 2\text{ MSS} + 1\text{ MSS} = 3\text{ MSS} \quad (\text{或 } 3000\text{ B}) $$
    - （注：当收到确认号为 3101 的 ACK 时，$\text{cwnd}$$ \text{增加至} $$4\text{ MSS} = \text{ssthresh}$，慢开始阶段结束，转入拥塞避免阶段）。
  - **第 3 轮（拥塞避免）**：当前 $\text{cwnd} = 4\text{ MSS}$$ \text{。H 连续发送 4 个 MSS（字节范围} $$3101 \sim 7100$）。
    - 拥塞避免算法规定：经过一个 RTT（即本轮所有报文段均被确认）后，$\text{cwnd}$ 线性增加 1 MSS。
    - 确认序号 7101 对应字节 7100 的下一个字节，表明本轮发送的 4 个 MSS 已全部得到确认。因此，收到 7101 的确认段时，标志着该轮 RTT 结束，$\text{cwnd}$ 线性加 1 调整为：
      $$ \text{cwnd} = 4\text{ MSS} + 1\text{ MSS} = 5\text{ MSS} \quad (\text{或 } 5000\text{ B}) $$

##### 第 (4) 问解析
- **时间推导**：
  - 建立数据连接：三次握手消耗 **$1\text{ RTT}$**。
  - 发送文件 $F$$ \text{（总大小} $$18000\text{ B} = 18\text{ MSS}$）：
    - 传输第 1 轮：$\text{cwnd} = 1\text{ MSS}$$ \text{，发送 1 MSS（累计发送 1 MSS），用时} $$1\text{ RTT}$。
    - 传输第 2 轮：$\text{cwnd} = 2\text{ MSS}$$ \text{，发送 2 MSS（累计发送 3 MSS），用时} $$1\text{ RTT}$。
    - 传输第 3 轮：$\text{cwnd} = 4\text{ MSS}$$ \text{，发送 4 MSS（累计发送 7 MSS），用时} $$1\text{ RTT}$。
    - 传输第 4 轮：$\text{cwnd} = 5\text{ MSS}$$ \text{，发送 5 MSS（累计发送 12 MSS），用时} $$1\text{ RTT}$。
    - 传输第 5 轮：此时剩余 $18 - 12 = 6\text{ MSS}$$ \text{。当前窗口} $$\text{cwnd} = 6\text{ MSS}$$ \text{，正好一次性发送 6 MSS（累计发送 18 MSS），用时} $$1\text{ RTT}$ 收到全部确认。
  - 数据传输阶段共用时 $5\text{ RTT}$。
  - 题目要求“从请求建立数据连接开始，到确认 F 已被服务器全部接收为止”，该终点界定在收到全部数据的最后一个 ACK 时，**不包含后续四次挥手断开的时间**。
  - 因此总用时至少为：
    $$T = T_{\text{conn}} + T_{\text{data}} = 1\text{ RTT} + 5\text{ RTT} = 6\text{ RTT} = 6 \times 10\text{ ms} = 60\text{ ms} = 0.06\text{ s}$$
- **平均发送速率计算**：
  - 传输的应用层数据量为 $18000\text{ B}$。
  - 平均速率为：
    $$v = \frac{18000\text{ B}}{0.06\text{ s}} = 300\text{ kB/s} = 300 \times 10^3\text{ B/s} = 0.3\text{ MB/s}$$
  - 若换算为网络比特率：
    $$ \text{v = \frac{18000 \times 8\text{ bit}}{0.06\text{ s}} = 2.4 \times 10^6\text{ bps} = 2.4\text{ Mb/s} \quad (\text{或 } 2.4\text{ Mbps})} $$

#### 正确答案
(1) FTP 控制连接是持久的；数据连接是非持久的；H 登录 FTP 服务器时，建立的是控制连接。  
(2) F 的第 1 个字节序号是 101；第二次挥手 ACK 段的确认序号是 18102。  
(3) 收到确认序号为 2101 的确认时，拥塞窗口调整为 3 MSS（或 3000B）；收到确认序号为 7101 的确认段时，拥塞窗口调整为 5 MSS（或 5000B）。  
(4) 至少需要 60 ms；期间应用层数据平均发送速率是 300 kB/s（或 0.3 MB/s、2.4 Mb/s）。

### 2022 年第 39 题

#### 题目题干
假设客户 C 和服务器 S 已建立一个 TCP 连接，通信往返时间 $\text{RTT} = 50\text{ ms}$$ \text{，最长报文段寿命} $$\text{MSL} = 800\text{ ms}$，数据传输结束后，C 主动请求断开连接。若从 C 主动向 S 发出 FIN 段时刻算起，则 C 和 S 进入 CLOSED 状态所需的时间至少分别是（ ）。

#### 选项设置
A. 850 ms, 50 ms  
B. 1650 ms, 50 ms  
C. 850 ms, 75 ms  
D. 1650 ms, 75 ms  

#### 考查知识点
1. 主动关闭方和被动关闭方四次挥手时间轴推导。
2. 报文段合并发送对最小时间的缩减效应。
3. TIME_WAIT 状态 $2\text{MSL}$ 计时器的计入规则。
4. 被动关闭方在 LAST_ACK 收到最终 ACK 后立即关闭的特性。

#### 逐步深度推导解析
设时刻 $t = 0$$ \text{为客户 C 主动向服务器 S 发出第一次挥手 `FIN` 段的时刻。单向传播时延为} $$0.5\text{ RTT} = 25\text{ ms}$。

```text
时刻 t (ms)       客户机 C                               服务器 S
  t = 0            [发出第一次挥手 FIN]
                   \
                    \ 单向传播 25ms
                     \
  t = 25              +-------------------------------> [收到 FIN, 无数据待发,
                                                         立即合并发出 ACK + FIN]
                     /                                  /
                    / 单向传播 25ms                    /
                   /                                  / 单向传播 25ms
  t = 50          [收到 S 的 FIN, 发出最终 ACK,       /
                   转入 TIME_WAIT, 启动 2MSL]         /
                   \                                 /
                    \ 单向传播 25ms                 /
                     \                             /
  t = 75              +---------------------------> [收到 ACK, 立即转入 CLOSED]
                                                    (S 进入 CLOSED 用时 75ms)
  ...
  t = 50 + 2MSL   [2MSL 计时器超时, 转入 CLOSED]
  = 1650ms        (C 进入 CLOSED 用时 1650ms)
```

##### 1. 服务器 S 进入 CLOSED 状态的最少时间
1. 在 $t = 0.5\text{ RTT} = 25\text{ ms}$ 时，S 收到 C 的 `FIN` 报文段。
2. 题目求解的是“所需的时间至少”，即最快场景。在最快情况下，S 没有需要向 C 发送的数据，因此 S 在收到 C 的 `FIN` 后，立即合并发送对 C 的确认 `ACK` 及 S 自己的释放请求 `FIN`（或将第二次和第三次挥手紧随连续发出，不耗费任何处理时延）。
3. S 发送的这个报文段经网络传播，历时 $0.5\text{ RTT} = 25\text{ ms}$$ \text{。在} $$t = 25 + 25 = 50\text{ ms}$ 时，C 收到 S 的 `FIN`。
4. C 收到 S 的 `FIN` 后，立即发出第四次挥手确认 `ACK`。
5. 该 `ACK` 经过单向传播时延 $0.5\text{ RTT} = 25\text{ ms}$ 到达服务器 S。此时刻为：
   $$ \text{t_S = 50\text{ ms} + 25\text{ ms} = 75\text{ ms} \quad (\text{即 } 1.5\text{ RTT})} $$
6. 服务器 S 处于 `LAST_ACK` 状态，一旦收到此最终 ACK，**立即转入 CLOSED 状态**，无需任何额外等待。因此 S 进入 CLOSED 状态的时间至少为 **75 ms**。

##### 2. 客户机 C 进入 CLOSED 状态的最少时间
1. 在 $t = 50\text{ ms}$ 时，C 收到 S 的 `FIN` 报文段并发出最终 `ACK`。
2. C 发出 ACK 后，**状态机转入 TIME_WAIT 状态**。
3. 按照 TCP 规范，主动关闭方在 TIME_WAIT 状态必须停留 $2\text{MSL}$ 时间。
4. 因此 C 进入 CLOSED 状态的时刻为：
   $$t_C = 50\text{ ms} + 2\text{MSL} = 50\text{ ms} + 2 \times 800\text{ ms} = 50\text{ ms} + 1600\text{ ms} = 1650\text{ ms}$$

#### 正确答案
**D**

### 2021 年第 38 题

#### 题目题干
若客户首先向服务器发送 FIN 段请求断开 TCP 连接，则当客户收到服务器发送的 FIN 段并向服务器发送了 ACK 段后，客户的 TCP 状态转换为（ ）。

#### 选项设置
A. CLOSE_WAIT  
B. TIME_WAIT  
C. FIN_WAIT_1  
D. FIN_WAIT_2  

#### 考查知识点
TCP 主动关闭方有限状态自动机（FSM）的迁移全流程。

#### 逐步深度推导解析
1. **状态机起点**：客户首先主动发起断开，向服务器发送 `FIN` 段，客户状态由 `ESTABLISHED` 转入 **`FIN_WAIT_1`**。
2. **中间过渡状态**：服务器收到该 `FIN` 后回复 `ACK`。客户收到该 `ACK` 后，状态由 `FIN_WAIT_1` 转入 **`FIN_WAIT_2`**，此时客户等待服务器发送 `FIN`。
3. **关键跃迁点**：服务器处理完数据后，向客户发送 `FIN` 段。客户收到此 `FIN` 段并向服务器回复了 `ACK` 段。根据 TCP 状态机定义，客户在此时刻的状态转入 **`TIME_WAIT`**。
4. **后续终止状态**：客户在 `TIME_WAIT` 状态启动 $2\text{MSL}$ 定时器，等待超时后最终转入 `CLOSED`。
5. 混淆项辨析：
   - `CLOSE_WAIT`：属于被动关闭方收到第一次挥手 FIN 后的状态。
   - `FIN_WAIT_1`：属于主动关闭方刚发出第一次挥手 FIN 后的状态。
   - `FIN_WAIT_2`：属于主动关闭方收到第二次挥手 ACK、尚未收到第三次挥手 FIN 时的半关闭状态。

#### 正确答案
**B**

### 2020 年第 39 题

#### 题目题干
若主机甲与主机乙建立 TCP 连接时发送的 SYN 段中的序号为 1000，在断开连接时，甲发送给乙的 FIN 段中的序号为 5001，则在无任何重传的情况下，甲向乙已经发送的应用层数据的字节数为（ ）。

#### 选项设置
A. 4002  
B. 4001  
C. 4000  
D. 3999  

#### 考查知识点
1. TCP 序号空间映射机制及控制位序号消耗准则。
2. 应用层数据字节流序号连续性推导。

#### 逐步深度推导解析
设甲向乙发送的应用层数据总字节数为 $L$。

##### 1. 建立连接阶段（SYN 序号占用）
- 甲发送给乙的 `SYN` 报文段中，序列号 $\text{seq}_{\text{SYN}} = 1000$。
- 根据准则一，`SYN` 报文段即便不携带任何数据，也必须消耗 1 个序号。
- 因此，甲后续发送的应用层数据的第一个字节，其序号为：
  $$\text{seq}_{\text{first}} = \text{seq}_{\text{SYN}} + 1 = 1000 + 1 = 1001$$

##### 2. 数据传输阶段（字节连续递增）
- 甲向乙共发送了 $L$ 字节的应用层数据，由于每个数据字节严格按序对应一个序列号，且无任何重传：
- 传输数据的最后一个字节，其序列号为：
  $$\text{seq}_{\text{last}} = \text{seq}_{\text{first}} + L - 1 = 1001 + L - 1 = 1000 + L$$

##### 3. 连接释放阶段（FIN 序号确定）
- 数据发送完毕后，甲发送 `FIN` 报文段请求断开连接。
- `FIN` 报文段的序列号字段，必须紧随其后取最后一个应用层数据字节序号的下一个序号：
  $$\text{seq}_{\text{FIN}} = \text{seq}_{\text{last}} + 1 = (1000 + L) + 1 = 1001 + L$$
- 题干已知断开连接时甲发送的 `FIN` 序号为 5001：
  $$ \text{1001 + L = 5001 \implies L = 5001 - 1001 = 4000\text{ 字节}} $$

##### 4. 几何区间推导验证
甲发送的数据字节序号区间为连续闭区间 $[1001, 5000]$。区间内包含的离散整数个数即为字节数：
$$ \text{L = 5000 - 1001 + 1 = 4000\text{ 字节}} $$
与代数推导结论完全吻合。

#### 正确答案
**C**

## 四、 综合解答题深度拓展及大题考法联动

### 1. 跨层综合考查模型深度拆解

在 408 综合大题（尤其是第 47 题）中，考官往往构建端到端网络拓扑，将物理层传输媒介、数据链路层 MTU、网络层 NAT/路由器转发、传输层 TCP 连接管理及应用层协议（HTTP/FTP）全面串联。四次挥手在该类大题中主要有三大考法切入点：

```text
+-----------------------------------------------------------------------------------+
| 跨层联动考法示意图                                                                |
|                                                                                   |
|  [应用层]      FTP控制连接(持久)和数据连接(非持久) / HTTP/1.0短连接及1.1长连接    |
|       |                                                                           |
|       v                                                                           |
|  [传输层]      TCP连接建立(3次握手) -> 慢开始/拥塞避免传输 -> 四次挥手释放(TIME_WAIT)|
|       |                                                                           |
|       v                                                                           |
|  [网络/链路层] IP数据报分片(MTU=1500B -> MSS=1460B) / 单向时延及往返时延(RTT)     |
+-----------------------------------------------------------------------------------+
```

#### 1.1 应用层及传输层连接生命周期联动
- **FTP 协议联动模型**：
  - 控制连接（默认端口 21）负责指令交互，在整个会话期间保持 ESTABLISHED 状态。
  - 数据连接（默认被动模式或主动模式端口 20）负责文件传输。每次文件传输完毕，**必须执行独立的四次挥手关闭数据连接**。大题常考查数据连接关闭时第二次挥手的确认号（如 2023 年第 47 题第 2 问）。
- **HTTP 协议联动模型**：
  - **HTTP/1.0 默认非持久连接**：每请求一个 Web 资源（HTML、图片等），均需完整经历“三次握手 $\to$$ \text{传输数据} $$\to$ 四次挥手”。若页面引用了 5 个图片，则需经历 6 次四次挥手过程，带来巨大的 RTT 开销。
  - **HTTP/1.1 默认持久连接（Keep-Alive）**：多个请求复用同一个 TCP 连接，直到显式设置首部字段 `Connection: close`，才由客户端或服务端发起四次挥手。

#### 1.2 传输层拥塞控制及总耗时推演联动
大题常考“从请求建立连接到某动作完成的总时间”。解此类题的关键在于**时间切片累加**：
$$ \text{T_{\text{total}} = T_{\text{握手}} + T_{\text{数据传输}} + T_{\text{释放}}} $$
- $$ \text{T_{\text{握手}}} $$：固定为 $1\text{ RTT}$（第三次握手发送数据）。
- $$ \text{T_{\text{数据传输}}} $$：严格按照 $\text{cwnd}$$ \text{增长序列（慢开始} $$1, 2, 4, 8\dots$$ \text{，达到} $$\text{ssthresh}$$ \text{后加} $$1$$ \text{）推算所需 RTT 轮次，每轮对应} $$1\text{ RTT}$。
- $$ \text{T_{\text{释放}}} $$：
  - 若问“确认数据被全部接收”，耗时截至数据最后一个 ACK 返回，**挥手耗时为 0**。
  - 若问“双方或单方进入 CLOSED 状态”，则必须精确计入四次挥手的网络往返及主动方的 $2\text{MSL}$。

### 2. Wireshark 抓包报文流及序列号推导通用解法

在 408 综合大题中，若给出 Wireshark 抓包表格或通信时序图，可利用**状态方程法**解决所有序列号和确认号推导：

#### 2.1 状态方程核心公式
对于任意报文段 $k$：
$$\text{Next\_Seq} = \text{Current\_Seq} + \text{Payload\_Len} + (\text{SYN ? } 1 : 0) + (\text{FIN ? } 1 : 0)$$
$$ \text{ACK\_Number} = \text{对端已连续成功接收的最高字节序号} + 1 $$

#### 2.2 Wireshark 四次挥手时序抓包典型模型表

```text
No.  Source  Dest  Flags          Seq     Ack     Len  State Change (Local)
---  ------  ----  ------------   -----   -----   ---  --------------------
1    Host_A  Srv_B [FIN, ACK]     18101   500     0    ESTABLISHED -> FIN_WAIT_1
2    Srv_B   Host_A [ACK]         500     18102   0    ESTABLISHED -> CLOSE_WAIT
3    Srv_B   Host_A [FIN, ACK]    500     18102   0    CLOSE_WAIT -> LAST_ACK
4    Host_A  Srv_B [ACK]         18102   501     0    FIN_WAIT_2 -> TIME_WAIT
```
- **第 1 包**：Host_A 发送 FIN，消耗序号 18101。
- **第 2 包**：Srv_B 回复 ACK，确认号为 $18101 + 1 = 18102$。此时 Srv_B 自身未发数据，其序列号保持 500。
- **第 3 包**：Srv_B 发送 FIN，序列号仍为 500。
- **第 4 包**：Host_A 回复 ACK，确认号为 $500 + 1 = 501$。Host_A 序号为 18102（纯 ACK 不消耗序号）。

### 3. 常见踩分点及失分陷阱防范

1. **陷阱一：忽视题干设问终点，盲目累加挥手时间**
   - **典型错误**：在 2023 年第 47 题第 (4) 问中，部分考生算出了握手及数据传输的 6 RTT 后，又机械地加上挥手所需的 1 RTT 或 2MSL。
   - **防错秘诀**：审视题干字眼。若问“到确认数据已被全部接收为止”，则收到数据尾字节的 ACK 即为终点；若问“到主机进入 CLOSED 状态为止”，才必须算入四次挥手及 TIME_WAIT。
2. **陷阱二：被动关闭方错误计入 2MSL**
   - **典型错误**：在 2022 年第 39 题中，误认为服务器 S 也要等待 2MSL 才能进入 CLOSED 状态，错选 B。
   - **防错秘诀**：牢记**只有主动发起关闭的一方才进入 TIME_WAIT 状态**！被动关闭方在 LAST_ACK 收到对端的 ACK 后立即进入 CLOSED。
3. **陷阱三：将序号偏移和传输字节数混淆（差 1 错误）**
   - **典型错误**：在 2020 年第 39 题中，直接用 $5001 - 1000 = 4001$。
   - **防错秘诀**：画数轴区间，或者使用标准状态方程：$\text{seq}_{\text{FIN}} = \text{ISN} + 1 + L$$ \text{，即} $$5001 = 1000 + 1 + L \implies L = 4000$。SYN 占用了第 1000 号，数据从 1001 开始。
4. **陷阱四：FTP 传输完毕后控制连接状态判断错误**
   - **典型错误**：误以为文件传输完毕后，FTP 控制连接也一起断开。
   - **防错秘诀**：控制连接是会话级别的，只有用户输入 `QUIT` 命令退出登录时，控制连接才会经历四次挥手关闭。

## 五、 考点速记清单

### 1. 核心状态转移速记口诀
> **主动方**：发 FIN 入 **WAIT_1**，收 ACK 进 **WAIT_2**，收 FIN 别忘发 ACK，**TIME_WAIT** 等两 MSL 入 **CLOSED**。  
> **被动方**：收 FIN 回 ACK 入 **CLOSE_WAIT**，发完数据发 FIN 入 **LAST_ACK**，收 ACK 直奔 **CLOSED** 不等待。  
> **同时关**：双发 FIN 入 **WAIT_1**，互收 FIN 进 **CLOSING**，收 ACK 齐聚 **TIME_WAIT**。

### 4. 经典避坑防错要点
1. **TIME_WAIT 存在方**：只有**主动发起关闭的一方**才会进入 TIME_WAIT 状态；被动方从 LAST_ACK 收到最终 ACK 后直接转入 CLOSED。
2. **2MSL 时间预算**：$1\text{ MSL}$$ \text{保证本端发送的 ACK 到达对端；另} $$1\text{ MSL}$ 保证对端可能超时重传的 FIN 返还本端。
3. **拥塞控制轮次及挥手阶段区分**：慢开始每轮翻倍（$1, 2, 4\dots$），拥塞避免每轮加 1；数据传完发起挥手，挥手不占用拥塞窗口。
4. **纯 ACK 不消耗序号**：在 Wireshark 分析或大题推导中，纯 ACK 报文段的序列号不消耗序号空间，其确认号严格等于期望收到的下一个字节序号。
