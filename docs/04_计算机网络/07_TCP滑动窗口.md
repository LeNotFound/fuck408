## 二、 具体考察内容

### 1. TCP 字节级滑动窗口模型

TCP 采用面向字节流（Byte Stream）的传输机制。虽然物理传输以报文段（Segment）为基本封装单位，但序号空间、确认机制和窗口滑动全部以单字节（Byte）为基准刻度。

#### (1) 序号与确认机制
- **序号（Sequence Number, seq）**：TCP 首部占 32 位。用于标识本报文段所发送的数据载荷的第一个字节在整个字节流中的绝对偏移位置。若数据载荷长度为 $L$ 字节，则该报文段所消耗的序号区间为 $[seq, \, seq + L - 1]$。
- **确认号（Acknowledgment Number, ack_seq）**：TCP 首部占 32 位。表示期望收到对方下一个报文段的首字节序号。
- **累积确认（Cumulative ACK）原则**：若确认号为 $ack\_seq = K$，代表序号小于 $K$ 的所有历史数据（即 $0$ 至 $K-1$ 范围内的全部字节）均已无差错、按序到达接收端。累积确认保证了即使网络中个别 ACK 报文发生丢失，后续更大的 ACK 也能隐式确认前面的所有数据段。

#### (2) 发送窗口物理分区与指针驱动模型
发送端的字节序列在任意时刻由发送窗口划分为四个逻辑区域，并通过三个状态指针实现动态维护：

```text
               已发送并收到确认     已发送但尚未确认      允许发送但尚未发送      不允许发送
            [已从套接字缓存移除]  [In-flight 未确认数据]  [可用窗口 Usable]    [超出窗口右边界]
       ------------------------+---------------------+-------------------+-------------------
       ... 2000 | 2001 ... 3000| 3001 ... 4000       | 4001 ... 5000     | 5001 ...
       ------------------------+---------------------+-------------------+-------------------
                               ^                     ^                   ^
                               |                     |                   |
                              P1                    P2                  P3
                               |<--- In-flight ----->|<-- Usable Win --->|
                               |<-------------- swnd ------------------->|
```

- **指针 $P_1$（发送窗口左边界）**：指向最早已发送但尚未收到确认的字节。$P_1$ 的数值严格等于当前收到的最大有效累积确认号 $ack\_seq$。
- **指针 $P_2$（待发送首字节指针）**：指向下一个即将封装入段发送的字节序号。
- **指针 $P_3$（发送窗口右边界）**：指向超出当前允许发送范围的第一个字节序号。由发送窗口大小 $swnd$ 决定：
  $$P_3 = P_1 + swnd$$
- **在途数据量（In-flight Bytes）**：已注入网络但未得到确认的载荷大小：
  $$\text{InFlight} = P_2 - P_1$$
- **可用发送窗口（Usable Window）**：发送端在未收到新确认之前，仍然被允许继续发送的字节配额：
  $$\text{UsableWindow} = P_3 - P_2 = swnd - \text{InFlight} = swnd - (P_2 - P_1)$$

#### (3) 窗口滑动行为判定
- **窗口合拢（左边界右移）**：当发送端收到递增的新 $ack\_seq$ 时，$P_1$ 向右推进，释放已确认的缓存，可用窗口空间相应扩大。
- **窗口张开（右边界右移）**：当网络拥塞缓解或接收端通告了更大的接收窗口时，$P_3$ 向右延伸，允许发送更多新数据。
- **窗口收缩（右边界左移）**：RFC 强烈建议协议实现避免显式收缩右边界，以防止与已经发出的在途数据产生冲突。

### 2. 发送窗口的综合约束：$\min(cwnd, rwnd)$ 原理

发送窗口的尺寸由网络承载能力（防拥塞）与对端处理能力（防溢出）协同决定，体现端到端流量控制和网络拥塞控制的联合约束。

```text
             +-----------------------+     +-----------------------+
             |    接收端流量控制     |     |    网络拥塞控制       |
             | 通告接收窗口 (rwnd)   |     |  拥塞窗口 (cwnd)      |
             +-----------+-----------+     +-----------+-----------+
                         \                             /
                          \                           /
                           v                         v
                       +---------------------------------+
                       | 发送窗口 swnd = min(cwnd, rwnd) |
                       +---------------------------------+
```

#### (1) 通告接收窗口（Receiver Window, rwnd）
接收端根据自身套接字接收缓存的空闲容量，在每个 TCP 首部的 16 位“窗口”（Window Size）字段填入当前空闲字节数。设接收端分配的总接收缓存容量为 $\text{RcvBuffer}$，已接收未被应用读取的数据字节数为 $\text{BufferedBytes}$，则：
$$rwnd = \text{RcvBuffer} - \text{BufferedBytes}$$

#### (2) 拥塞窗口（Congestion Window, cwnd）
发送端根据网络往返时延（RTT）及丢包/拥塞反馈动态调整的状态变量，其演化规律遵循慢开始（Slow Start）、拥塞避免（Congestion Avoidance）、快重传与快恢复算法：
- **慢开始阶段（$cwnd < ssthresh$）**：每收到 1 个对新报文段的 ACK，拥塞窗口线性增加 $1\text{ MSS}$；每经过 1 个 RTT，拥塞窗口呈指数倍增（$cwnd \leftarrow 2 \times cwnd$）。
- **拥塞避免阶段（$cwnd \ge ssthresh$）**：每经过 1 个 RTT，拥塞窗口仅线性增加 $1\text{ MSS}$（即每个有效 ACK 增加 $\frac{\text{MSS} \times \text{MSS}}{cwnd}$ 字节）。

#### (3) 实际可用发送额度推导公式
发送端可连续注入网络的数据上限受到双重截断：
$$swnd = \min(cwnd, rwnd)$$
在特定时刻，若发送端已向网络发出若干段数据，未收到新确认前**还可以继续发送的数据段数**为：
$$\text{AvailableSegments} = \left\lfloor \frac{\min(cwnd, rwnd) - \text{InFlight}}{\text{MSS}} \right\rfloor$$
这是解答选择题（如 2025#38、2021#40）的核心计算模型。

### 3. 流量控制、零窗口死锁与持续计时器

#### (1) 零窗口通告（Zero Window Advertisement）
当接收端应用程序消费数据的速率远低于网络到达速率时，接收缓存最终会被完全填满。此时接收端回复的 ACK 首部中通告 $rwnd = 0$。发送端收到该报文后，发送窗口收缩为 0，必须立刻暂停发送任何普通数据段。

#### (2) 零窗口死锁问题（Deadlock Scenario）
零窗口产生后，通信双方进入等待状态：
1. 接收端应用程序随后读取数据，释放了接收缓存，接收端因此生成一个通告 $rwnd = W > 0$ 的非零窗口更新报文（Window Update ACK）。
2. TCP 协议规定，纯 ACK 报文（不含数据载荷且非 SYN/FIN）不占用序号空间，也不由对端进行确认（即 ACK 不需要被确认）。
3. 若此非零窗口更新报文在网络传输中发生丢失或损坏丢弃，发送端将永远等待对端的窗口更新报文；而接收端则认为自身已经完成通告，静默等待发送端传输新数据。
4. 双方互相无限期等待对方的报文，形成**零窗口死锁（Zero Window Deadlock）**。

```text
       发送端 (Sender)                                接收端 (Receiver)
              |                                              |
              |            rwnd = 0 (接收缓存已满)           |
              |<---------------------------------------------| (发送端启动持续计时器)
              |                                              |
      [暂停发送普通数据]                                [应用读取数据，释放缓存]
              |                                              |
              |           rwnd = 2000B (窗口更新报文)        |
              |       X <------------------------------------| (该报文在网络中丢失!)
              |                                              |
    [仍认为 rwnd = 0]                                [等待发送端发送数据]
              |                                              |
              |================== 死锁形成 ==================|
              |                                              |
              | (持续计时器超时)                             |
              |            零窗口探测报文 (ZWP, 1B 数据)      |
              |--------------------------------------------->|
              |                                              |
              |            ACK, ack_seq, rwnd = 2000B        |
              |<---------------------------------------------| (死锁解除!)
              |                                              |
      [恢复正常滑动窗口发送]                                 |
```

#### (3) 持续计时器（Persistence Timer）工作机制
为了彻底打破零窗口死锁，TCP 发送方引入了持续计时器：
- **触发启动**：只要发送方接收到对端通告的零窗口报文（$rwnd = 0$），便立即启动该连接的持续计时器。
- **探测报文发送**：当持续计时器超时（Timer Expires）时，发送方强制向接收方发送一个极小的探测报文段——**零窗口探测报文（Zero Window Probe, ZWP）**。
- **探测报文特征**：ZWP 通常仅携带 1 字节数据载荷，或者使用一个无需占用序号空间的特殊探测探测段。
- **接收端强制响应**：接收端在收到探测报文后，必须强制回复一个 ACK 报文段，并在首部通告当前的最新接收窗口值：
  - 若接收缓存仍然为 0，返回的 ACK 依然通告 $rwnd = 0$。发送端重置持续计时器，通常采用指数退避算法（Exponential Backoff）延长超时周期（通常设定上限为 60 秒），随后继续周期性探测。
  - 若接收缓存已腾出空间，返回的 ACK 通告 $rwnd > 0$。死锁被打破，发送端依据通告值更新发送窗口，恢复数据发送。

### 4. 易混概念深度辨析

#### 辨析一：数据链路层滑动窗口协议和传输层TCP滑动窗口
- **数据链路层**：以物理“帧”（Frame）为基本调度单位。序号空间较小（如 3 比特编码 $0 \sim 7$），窗口尺寸在连接建立后固定不变（如后退N帧协议 GBN 发送窗口最大为 $2^n-1$，选择重传协议 SR 发送窗口最大为 $2^{n-1}$）。
- **传输层 TCP**：以“字节”（Byte）为基本调度单位。序号空间达 32 位（$0 \sim 2^{32}-1$），窗口大小并非静态常量，而是根据拥塞状况 $cwnd$ 与接收能力 $rwnd$ 实时、动态、连续收缩和扩张。

#### 辨析二：发送窗口大小（swnd）和可用发送窗口（Usable Window）
- **发送窗口大小（$swnd$）**：表示在当前网络和对端能力约束下，从最早未确认字节算起，总共被允许注入网络的最大连续字节区间跨度，数值上等于 $\min(cwnd, rwnd)$。
- **可用发送窗口（Usable Window）**：表示发送端此时此刻“还可以继续发送”的字节额度。必须在 $swnd$ 基础上严格减去当前在途但尚未被确认的 In-flight 数据量。

#### 辨析三：套接字发送/接收缓存空间和发送/接收窗口
- **缓存（Buffer）**：物理内存实体。发送缓存保存应用程序写入但尚未成功发送的数据，以及已经发送但尚未收到确认的数据；接收缓存保存按序到达未被读取的数据，以及乱序到达的数据。
- **窗口（Window）**：逻辑许可范围。发送窗口仅是发送缓存中的一个活动子集；接收窗口仅是接收缓存中当前尚未被占用的剩余空闲子集。窗口大小永远不可能超过对应的总缓存物理容量。

### 2025 年 408 统考真题（第 38 题）

#### 题目呈现
主机甲通过 TCP 向主机乙发送数据的部分过程如下图，seq 为序号，ack_seq 为确认序号，rcwnd 为接收窗口。甲在 $t_0$ 时刻的拥塞窗口和发送窗口均为 $2000\text{ B}$，拥塞控制阈值为 $8000\text{ B}$，$\text{MSS}=1000\text{ B}$。甲始终以 MSS 发送 TCP 段。若甲在 $t_1$ 时刻收到如图所示的确认段，则甲在未收到新的确认段之前，还可以继续向乙发送的 TCP 段数是（ ）。

```text
       主机甲                                 主机乙
         |                                      |
     t0  |---- seq=2001, 1000B 数据 ----------->|
         |---- seq=3001, 1000B 数据 ----------->|
         |                                      |
         |<--- ack_seq=3001, rcwnd=4000B -------|
     t1  |                                      |
         v                                      v
```

A. 2  
B. 3  
C. 4  
D. 5  

#### 深入推导
1. **分析 $t_0$ 时刻的初始状态**：
   - 拥塞窗口 $cwnd = 2000\text{ B} = 2\text{ MSS}$。
   - 慢开始门限 $ssthresh = 8000\text{ B} = 8\text{ MSS}$。
   - 因 $cwnd < ssthresh$，主机甲当前处于**慢开始阶段**。
   - 甲在 $t_0$ 时刻连续发出两个报文段：
     - 段 1：$seq = 2001$，载荷 $1000\text{ B}$，所占字节序号范围为 $[2001, \, 3000]$。
     - 段 2：$seq = 3001$，载荷 $1000\text{ B}$，所占字节序号范围为 $[3001, \, 4000]$。
2. **分析 $t_1$ 时刻收到的确认段及拥塞窗口更新**：
   - 收到确认段：$ack\_seq = 3001$，$rcwnd = 4000\text{ B} = 4\text{ MSS}$。
   - 确认号 $ack\_seq = 3001$ 表明段 1（$[2001, \, 3000]$）已被乙成功按序接收，而段 2 尚未被确认。
   - 主机甲收到针对段 1 的有效新确认，在慢开始算法中，每收到一个新确认段，拥塞窗口增加 $1\text{ MSS}$：
     $$cwnd_{\text{new}} = cwnd + 1\text{ MSS} = 2\text{ MSS} + 1\text{ MSS} = 3\text{ MSS} = 3000\text{ B}$$
3. **计算更新后的发送窗口**：
   - 此时通告接收窗口 $rwnd = 4000\text{ B} = 4\text{ MSS}$。
   - 根据双重约束机制，新的发送窗口为：
     $$swnd = \min(cwnd_{\text{new}}, rwnd) = \min(3\text{ MSS}, 4\text{ MSS}) = 3\text{ MSS} = 3000\text{ B}$$
4. **计算在途数据量与剩余可发送段数**：
   - 此时段 2（$seq = 3001$，长度 $1000\text{ B}$）已经注入网络但未得到确认，占用 In-flight 额度：
     $$\text{InFlight} = 1000\text{ B} = 1\text{ MSS}$$
   - 在未收到新确认段之前，甲还能够继续发送的数据量为：
     $$\text{UsableWindow} = swnd - \text{InFlight} = 3\text{ MSS} - 1\text{ MSS} = 2\text{ MSS}$$
   - 因甲始终以 MSS 发送段，故允许继续发送的 TCP 段数为：
     $$\text{Segments} = \frac{2\text{ MSS}}{1\text{ MSS}} = 2$$

#### 正确答案
**A**

### 2023 年 408 统考真题（第 47 题）

#### 题目呈现
主机 H 登录到 FTP 服务器后，向服务器上传一个大小为 $18000\text{ B}$ 的文件 F。假设 H 传输 F 建立数据连接时，选择的初始序号为 100，$\text{MSS} = 1000\text{ B}$，拥塞控制的初始阈值是 $4\text{ MSS}$，$\text{RTT} = 10\text{ ms}$，忽略 TCP 的传输时延。在 F 的传送过程中，H 以 MSS 段向服务器发送数据，且始终没有错误、丢包和乱序。

```text
       主机 H                                         FTP 服务器
         |                                                |
         |==== 建立控制连接 (端口 21) =====================|
         |                                                |
         |---- 请求建立数据连接 (SYN, seq=100) ---------->|
         |<--- 响应 (SYN+ACK) ----------------------------|
         |---- 建立确认 (ACK) ---------------------------->|
         |                                                |
         |==== 数据传输阶段 (上传 18000B 文件 F) =========|
         |                                                |
         |---- 释放数据连接 (FIN) ------------------------>|
         |<--- 释放确认 (ACK) ----------------------------|
```

请回答下列问题：
1. FTP 的控制连接是持久的还是非持久的？FTP 的数据连接是持久的还是非持久的？H 登录服务器时，建立的 FTP 连接是数据连接还是控制连接？
2. H 通过数据连接发送 F 时，F 的第一个字节序号是多少？在断开数据连接的过程中，FTP 发送的第二次挥手的 ACK 序号是多少？
3. F 发送过程中，当 H 收到确认序号为 2101 的确认时，H 的拥塞窗口调整为多少？收到确认序号为 7101 的确认段时，H 的拥塞窗口调整为多少？
4. H 从请求建立数据连接开始，到确认 F 已被服务器全部接收为止，至少要多长时间？期间应用层数据平均发送速率是多少？

#### 深入推导
1. **问题 (1) 解析（应用层协议特性）**：
   - FTP 协议采用双连接架构，将控制命令和数据传输分离。
   - 控制连接（默认端口 21）在整个会话期间保持打开状态，属于**持久连接**。
   - 数据连接（默认端口 20）仅在传输文件或目录列表时动态按需建立，传输完毕立即关闭，属于**非持久连接**。
   - 用户登录验证、权限交互全部在控制连接上完成，故登录时建立的是**控制连接**。

2. **问题 (2) 解析（序号消耗与连接释放）**：
   - 数据连接建立时，H 发送的 SYN 段携带初始序号 $seq = 100$。TCP 协议规定，SYN 段不携带应用层数据，但必须**消耗一个序号**。
   - 因此，随后的第一个承载数据的数据段首字节序号为：
     $$seq_{\text{first}} = 100 + 1 = 101$$
   - 文件 F 大小为 $18000\text{ B}$，所占用的连续序号空间为 $[101, \, 101 + 18000 - 1] = [101, \, 18100]$。
   - 数据传输完成后，进入 TCP 四次挥手流程：
     - 第一次挥手：H 向服务器发送释放报文段，其序号为数据结束后的下一个序号，即 $seq = 18101$（置 $\text{FIN} = 1$）。
     - 第二次挥手：服务器向 H 回复确认报文段。因为 FIN 报文段同样不携带数据但**消耗一个序号**，服务器期望收到的下一个字节序号为：
       $$ack\_seq = 18101 + 1 = 18102$$

3. **问题 (3) 解析（滑动窗口与拥塞控制状态演化）**：
   - 建立连接后，初始拥塞窗口 $cwnd = 1\text{ MSS} = 1000\text{ B}$，慢开始阈值 $ssthresh = 4\text{ MSS}$。
   - 各传输轮次发送段的序号范围与确认追踪：
     - **第 1 轮次**：$cwnd = 1\text{ MSS}$。发送 1 个段，序号 $[101, \, 1100]$。
       收到服务器针对该段的确认，确认号为 $1101$。此时处于慢开始阶段，$cwnd$ 增加 $1\text{ MSS}$，变为 $cwnd = 2\text{ MSS}$。
     - **第 2 轮次**：$cwnd = 2\text{ MSS}$。发送 2 个段：
       - 段 A：序号 $[1101, \, 2100]$。
       - 段 B：序号 $[2101, \, 3100]$。
       - 当 H 收到确认序号为 $2101$ 的 ACK 时，是对段 A 的确认。慢开始阶段每收到 1 个确认便增加 $1\text{ MSS}$，故拥塞窗口调整为：
         $$cwnd = 2\text{ MSS} + 1\text{ MSS} = 3\text{ MSS}$$
       - 随后收到对段 B 的确认（确认号为 $3101$），$cwnd$ 增至 $4\text{ MSS}$，此时达到慢开始门限 $ssthresh = 4\text{ MSS}$，转入**拥塞避免阶段**。
     - **第 3 轮次**：发送 4 个段，覆盖序号 $[3101, \, 7100]$。
       该轮次末尾，服务器发回确认序号为 $7101$ 的确认段，这标志着该传输轮次的 4 个段已全部被成功确认，经过了 1 个完整的 RTT。
       在拥塞避免阶段，每个 RTT 窗口线性增加 $1\text{ MSS}$。因此，当收到确认号 $7101$ 时，拥塞窗口调整为：
       $$cwnd = 4\text{ MSS} + 1\text{ MSS} = 5\text{ MSS}$$

4. **问题 (4) 解析（总时延模型与传输速率推算）**：
   - **传输轮次时延分析**：
     - **连接建立阶段**：数据连接的三次握手完成需要耗费 $1\text{ RTT}$（H 发送 SYN 到收到 SYN+ACK，第三次握手的 ACK 段可同时搭载数据段）。
     - **数据传输各轮次**（题干忽略传输时延，各轮次耗时即为 $1\text{ RTT}$）：
       - 轮次 1：$cwnd = 1\text{ MSS}$，传输 $1000\text{ B}$（累计传输 $1000\text{ B}$），耗时 $1\text{ RTT}$。
       - 轮次 2：$cwnd = 2\text{ MSS}$，传输 $2000\text{ B}$（累计传输 $3000\text{ B}$），耗时 $1\text{ RTT}$。
       - 轮次 3：$cwnd = 4\text{ MSS}$，传输 $4000\text{ B}$（累计传输 $7000\text{ B}$），耗时 $1\text{ RTT}$。
       - 轮次 4：$cwnd = 5\text{ MSS}$，传输 $5000\text{ B}$（累计传输 $12000\text{ B}$），耗时 $1\text{ RTT}$。
       - 轮次 5：$cwnd = 6\text{ MSS}$。剩余数据量为 $18000\text{ B} - 12000\text{ B} = 6000\text{ B} = 6\text{ MSS}$。正好在该轮次全部发出并收到确认，耗时 $1\text{ RTT}$。
     - 数据传输阶段共耗费 $5\text{ RTT}$。
   - **总耗时**：
     $$T_{\text{total}} = 1\text{ RTT (握手)} + 5\text{ RTT (数据传输)} = 6\text{ RTT} = 6 \times 10\text{ ms} = 60\text{ ms}$$
   - **应用层数据平均发送速率**：
     - 应用层有效数据量为 $18000\text{ B}$：
       $$\text{Rate} = \frac{18000\text{ B}}{60\text{ ms}} = \frac{18000\text{ Byte}}{0.06\text{ s}} = 300\text{ KB/s} = 300 \times 10^3\text{ B/s}$$
     - 换算为比特率（注意题干单位换算约定）：
       $$\text{BitRate} = 300 \times 10^3 \times 8\text{ bps} = 2.4 \times 10^6\text{ bps} = 2.4\text{ Mbps}$$

#### 规范解答结论
1. 控制连接是持久的；数据连接是非持久的；H 登录服务器时建立的是控制连接。
2. F 的第一个字节序号为 101；第二次挥手 ACK 的序号为 18102。
3. 收到确认序号为 2101 的确认时，拥塞窗口调整为 $3\text{ MSS}$（或 $3000\text{ B}$）；收到确认序号为 7101 的确认段时，拥塞窗口调整为 $5\text{ MSS}$（或 $5000\text{ B}$）。
4. 至少需要 $60\text{ ms}$；应用层数据平均发送速率为 $300\text{ KB/s}$（即 $2.4\text{ Mbps}$ 或 $300 \times 10^3\text{ B/s}$）。

### 2021 年 408 统考真题（第 40 题）

#### 题目呈现
设主机甲通过 TCP 向主机乙发送数据，部分过程如下图所示。甲在 $t_0$ 时刻发送一个序号 $seq=501$、封装 $200\text{ B}$ 数据的段，在 $t_1$ 时刻收到乙发送的序号 $seq = 601$、确认序号 $ack\_seq = 501$、接收窗口 $rcvwnd = 500\text{ B}$ 的段，则甲在未收到新的确认段之前，可以继续向乙发送的数据序号范围是（ ）。

```text
       主机甲                                 主机乙
         |                                      |
     t0  |---- seq=501, 200B 数据 ------------->|
         |                                      |
         |<--- seq=601, ack_seq=501, rcvwnd=500B|
     t1  |                                      |
         v                                      v
```

A. 501 ~ 1000  
B. 601 ~ 1100  
C. 701 ~ 1000  
D. 801 ~ 1100  

#### 深入推导
1. **确定发送窗口的左右物理边界**：
   - 乙通告的确认序号 $ack\_seq = 501$，表示乙当前期望收到的首字节为 501，说明序号 501 及其之后的数据尚未被确认。
   - 因此，主机甲的发送窗口**左边界**锚定在 $P_1 = 501$。
   - 乙通告的接收窗口 $rcvwnd = 500\text{ B}$，由于未提及拥塞控制限制，发送窗口由接收窗口决定，大小为 $500\text{ B}$。
   - 发送窗口所覆盖的闭区间为：
     $$[\text{左边界}, \, \text{右边界}] = [501, \, 501 + 500 - 1] = [501, \, 1000]$$
2. **分析已发送但未确认的数据（In-flight 数据）**：
   - 甲在 $t_0$ 时刻已经发出了 $seq = 501$ 且包含 $200\text{ B}$ 载荷的报文段。
   - 该报文段占用的序号区间为 $[501, \, 501 + 200 - 1] = [501, \, 700]$。
   - $t_1$ 时刻收到的确认号为 $ack\_seq = 501$，表明乙并未对 $[501, \, 700]$ 进行确认（该确认段可能是乙在收到 501 之前发出的，或 501 报文仍在途中/产生乱序）。
   - 因此序号 $501 \sim 700$ 属于**已发送但尚未确认的在途数据**，其下一个待发送的字节指针已经移动至 $P_2 = 701$。
3. **计算允许继续发送的序号范围**：
   - 题目考查的是甲“可以继续向乙发送”的数据序号范围，即可用窗口（Usable Window）对应的序号区间。
   - 发送端不能重复发送处于可用窗口之外的数据，也不能重复发送已经处于 In-flight 状态的数据。
   - 可用窗口的起始序号为 $P_2 = 701$；
   - 可用窗口的截止序号为窗口右边界 1000。
   - 因此，甲在未收到新的确认段之前，能够继续发送的数据序号范围为 $701 \sim 1000$（可用字节量为 $1000 - 701 + 1 = 300\text{ B}$，正好等于 $500\text{ B} - 200\text{ B} = 300\text{ B}$）。

#### 正确答案
**C**

### 2016 年 408 统考真题（第 41 题）

#### 题目呈现
假设主机 H3 访问 Web 服务器 S 时，S 为新建的 TCP 连接分配了 $20\text{ KB}$（$1\text{ KB} = 1024\text{ B}$）的接收缓存，最大段长 $\text{MSS} = 1\text{ KB}$，平均往返时间 $\text{RTT} = 200\text{ ms}$。H3 建立连接时的初始序号为 100，且持续以 MSS 大小的段向 S 发送数据，拥塞窗口初始阈值为 $32\text{ KB}$；S 对收到的每个段进行确认，并通告新的接收窗口。假定 TCP 连接建立完成后，S 端的 TCP 接收缓存仅有数据存入而无数据取出。请回答下列问题：

1. 在 TCP 连接建立过程中，H3 收到的 S 发送过来的第二次握手 TCP 段的 SYN 和 ACK 标志位的值分别是多少？确认序号是多少？
2. H3 收到的第 8 个确认段所通告的接收窗口是多少？此时 H3 的拥塞窗口变为多少？H3 的发送窗口变为多少？
3. 当 H3 的发送窗口等于 0 时，下一个待发送的数据段序号是多少？H3 从发送第 1 个数据段到发送窗口等于 0 时刻为止，平均数据传输速率是多少（忽略段的传输延时）？
4. 若 H3 与 S 之间通信已经结束，在 $t$ 时刻 H3 请求断开该连接，则从 $t$ 时刻起，S 释放该连接的最短时间是多少？

#### 深入推导
1. **问题 (1) 解析（三次握手参数）**：
   - 第一次握手：H3 向 S 发送连接请求报文段，$\text{SYN} = 1, \text{ACK} = 0, seq = 100$。
   - 第二次握手：服务器 S 收到请求后，回复确认及同步报文段。此时同步位与确认位均置 1，即 $\text{SYN} = 1, \text{ACK} = 1$。
   - 确认序号规则：SYN 报文段消耗 1 个序号，故 S 回复的确认号为：
     $$ack\_seq = 100 + 1 = 101$$

2. **问题 (2) 解析（缓存无读取模型与发送窗口计算）**：
   - **通告接收窗口 $rwnd$ 计算**：
     题目设定接收缓存为 $20\text{ KB}$，且“仅有数据存入而无数据取出”。S 对收到的每个段（大小为 $1\text{ KB}$）进行确认。当收到第 8 个确认段时，说明 S 已接收并存入了 8 个数据段，共占用缓存空间 $8 \times 1\text{ KB} = 8\text{ KB}$。
     因此接收缓存剩余空闲容量为：
     $$rwnd = 20\text{ KB} - 8\text{ KB} = 12\text{ KB}$$
   - **拥塞窗口 $cwnd$ 计算**：
     连接建立后，慢开始初始 $cwnd = 1\text{ MSS} = 1\text{ KB}$，门限 $ssthresh = 32\text{ KB}$。
     在慢开始算法中，发送方每收到一个对新数据段的确认，拥塞窗口增加 $1\text{ MSS}$。
     H3 累计收到了 8 个确认段，因此拥塞窗口增加了 $8\text{ KB}$：
     $$cwnd = 1\text{ KB} + 8 \times 1\text{ KB} = 9\text{ KB}$$
     此时 $cwnd = 9\text{ KB} < ssthresh = 32\text{ KB}$，仍处于慢开始阶段。
   - **发送窗口 $swnd$ 计算**：
     发送窗口受限于拥塞窗口和接收窗口的极小值：
     $$swnd = \min(cwnd, rwnd) = \min(9\text{ KB}, 12\text{ KB}) = 9\text{ KB}$$

3. **问题 (3) 解析（零窗口到达推导与平均速率计算）**：
   - **待发送序号推导**：
     当 H3 的发送窗口等于 0 时，由 $swnd = \min(cwnd, rwnd) = 0$ 可知，接收端缓存已被全部填满，通告的 $rwnd = 0$。
     此时接收端已完全存入 $20\text{ KB}$ 数据，即 $20 \times 1024\text{ B} = 20480\text{ B}$。
     数据首字节序号为 101，已注入接收缓存的数据字节序号区间为：
     $$[101, \, 101 + 20480 - 1] = [101, \, 20580]$$
     因此，下一个待发送的数据段的首字节序号为：
     $$seq_{\text{next}} = 101 + 20480 = 20581$$
   - **传输轮次与耗时追踪**：
     由于接收缓存不取出数据，各轮次发送量受到慢开始 $cwnd$ 和剩余缓存空间双重制约：
     - **第 1 轮次**：$cwnd = 1\text{ KB}$。发送 1 个段（1KB），S 缓存剩余 19KB。耗时 $1\text{ RTT}$，收到确认后 $cwnd$ 翻倍变为 $2\text{ KB}$。
     - **第 2 轮次**：$cwnd = 2\text{ KB}$。发送 2 个段（2KB），S 缓存剩余 17KB。耗时 $1\text{ RTT}$，收到确认后 $cwnd$ 翻倍变为 $4\text{ KB}$。
     - **第 3 轮次**：$cwnd = 4\text{ KB}$。发送 4 个段（4KB），S 缓存剩余 13KB。耗时 $1\text{ RTT}$，收到确认后 $cwnd$ 翻倍变为 $8\text{ KB}$。
     - **第 4 轮次**：$cwnd = 8\text{ KB}$。发送 8 个段（8KB），S 缓存剩余 5KB。耗时 $1\text{ RTT}$，收到确认后 $cwnd$ 翻倍变为 $16\text{ KB}$。
     - **第 5 轮次**：此时发送方 $cwnd = 16\text{ KB}$，但接收方通告的接收窗口仅剩 $rwnd = 5\text{ KB}$。受限于接收窗口，发送方在本轮次只能发送：
       $$swnd = \min(16\text{ KB}, 5\text{ KB}) = 5\text{ KB}$$
       发送 5 个段（5KB）后，接收缓存完全耗尽（剩余 0KB）。耗时 $1\text{ RTT}$ 后收到确认，通告 $rwnd = 0$，发送窗口收缩为 0。
     - 从发送第 1 个数据段开始到发送窗口等于 0 为止，整整历经 5 个传输轮次：
       $$T = 5 \times \text{RTT} = 5 \times 200\text{ ms} = 1000\text{ ms} = 1\text{ s}$$
   - **平均数据传输速率推算**：
     在此期间总共传输的应用层数据量为 $20\text{ KB}$：
     $$\text{Rate} = \frac{20\text{ KB}}{1\text{ s}} = 20\text{ KB/s}$$
     若转换为比特率表示（以二进制计量）：
     $$\text{BitRate} = 20 \times 1024 \times 8\text{ bps} = 163840\text{ bps} = 163.84\text{ kbps}$$
     （注：若按十进制标准速率计算亦可写作 $20.48\text{ kB/s}$ 或 $163.84\text{ kbps}$，评分标准中直接给出 $20\text{ KB/s}$ 或对应的比特率换算均可得分）。

4. **问题 (4) 解析（四次挥手最短释放时间）**：
   - 考查正常断开连接时的时延边界：
     - $t$ 时刻，H3 向 S 发送连接释放段（FIN），用时 $0.5\text{ RTT}$ 到达 S。
     - S 收到 FIN 后，发出 ACK 确认段（用时 $0.5\text{ RTT}$ 到达 H3）。因为 S 此时已经没有任何数据需要发送，故 S 可以紧接着同时（或合并）发出自己的 FIN 段。
     - H3 收到 S 的 FIN 段后，立即向 S 发送最终确认 ACK（用时 $0.5\text{ RTT}$ 到达 S）。
     - S 收到来自 H3 的最终 ACK 报文段后，立即彻底释放连接（关闭连接）。
   - 因此，从 $t$ 时刻起，S 释放该连接的最短单向时延总和为：
     $$\Delta t = 0.5\text{ RTT (H3发FIN)} + 0.5\text{ RTT (S发FIN/ACK)} + 0.5\text{ RTT (H3发ACK)} = 1.5\text{ RTT}$$
     代入 $\text{RTT} = 200\text{ ms}$：
     $$\Delta t = 1.5 \times 200\text{ ms} = 300\text{ ms}$$

#### 规范解答结论
1. 第二次握手 TCP 段的 $\text{SYN} = 1, \text{ACK} = 1$；确认序号是 101。
2. 第 8 个确认段通告的接收窗口是 $12\text{ KB}$；此时拥塞窗口变为 $9\text{ KB}$；发送窗口变为 $9\text{ KB}$。
3. 当发送窗口等于 0 时，下一个待发送段的序号是 20581；从发送第 1 个段到发送窗口等于 0 的平均数据传输速率是 $20\text{ KB/s}$（或 $163.84\text{ kbps}$）。
4. 从 $t$ 时刻起，S 释放该连接的最短时间是 $300\text{ ms}$。

### 统考历史经典真题选讲

#### 2013 年 408 统考真题（第 39 题）
**题目**：主机甲与主机乙之间已建立一个 TCP 连接，双方持续有数据传输，且数据无差错与丢失。若甲收到 1 个来自乙的 TCP 段，该段的序号为 1913、确认序号为 2046、有效载荷为 100 字节，则甲立即发送给乙的 TCP 段的序号和确认序号分别是（ ）。  
A. 2046、2012  
B. 2046、2013  
C. 2047、2012  
D. 2047、2013  

**深度解析**：
1. 乙发送给甲的报文中，确认号 $ack = 2046$，意味着乙期望收到甲发送的数据从序号 2046 开始。因此，甲接下来发送给乙的报文段的首字节序号必须为：
   $$seq_{\text{甲}} = 2046$$
2. 乙发送的报文段序号为 $seq_{\text{乙}} = 1913$，载荷为 $100\text{ B}$，其占用的序号区间为 $[1913, \, 1913 + 100 - 1] = [1913, \, 2012]$。
3. 甲在正确接收到该段后，期望收到乙发送的下一个字节序号为：
   $$ack_{\text{甲}} = 2012 + 1 = 2013$$
故甲发给乙的段中，序号为 2046，确认序号为 2013。  
**【正确答案】B**

## 四、 综合解答题深度拓展与大题考法联动

在 408 综合大题（尤其是网络层与传输层综合应用大题，如第 47 题）中，TCP 滑动窗口很少作为孤立知识点考查，而是作为跨层机制的汇聚核心。备考必须掌握以下系统化推导方法与应试技巧。

### 1. 综合大题的核心命题框架

```text
                  +----------------------------------------------+
                  |              应用层协同特征                  |
                  |  - FTP：双连接架构 (控制持久, 数据非持久)     |
                  |  - HTTP：非持久/持久连接, 并发窗口限制        |
                  +----------------------+-----------------------+
                                         |
                                         v
                  +----------------------------------------------+
                  |              传输层核心状态机                |
                  |  - 三次握手/四次挥手：消耗序号规则 (SYN/FIN)  |
                  |  - 状态演化：慢开始 -> 拥塞避免 (ssthresh)    |
                  |  - 双重限流：swnd = min(cwnd, rwnd)          |
                  |  - 流量控制：零窗口通告与持续计时器探测       |
                  +----------------------+-----------------------+
                                         |
                                         v
                  +----------------------------------------------+
                  |              底层网络传输开销                |
                  |  - 往返时延 RTT：以传输轮次 (Round) 为步进    |
                  |  - 物理速率与时延：传输时延 vs 往返传播时延  |
                  |  - MTU 与 MSS：TCP分段与网络层分片关系        |
                  +----------------------------------------------+
```

### 2. 传输轮次（Round）的离散化模拟法（“列表法”）
面对大题中复杂的窗口动态演化，切忌使用连续微积分公式，应在草稿纸上采用“离散传输轮次追踪表”。
- **步骤 1：列出初始约束**：记录初始 $cwnd$、慢开始门限 $ssthresh$、初始接收缓存大小、数据总长度及起始 $seq$。
- **步骤 2：逐轮次构建状态矩阵**：
  - 记录第 $k$ 轮次开始时的 $cwnd$ 和 $rwnd$。
  - 计算本轮次实际发送的窗口额度：$W_k = \min(cwnd, rwnd)$。
  - 检查本轮次发送的数据段是否会受限于剩余总数据量。
  - 更新对端接收缓存剩余量：$rwnd \leftarrow rwnd - \text{本轮存入量} + \text{本轮应用读取量}$。
  - 根据收到的 ACK 模式（整轮确认还是分段确认）更新下一轮次的 $cwnd$。
- **步骤 3：累加时延**：每个传输轮次严格计为 $1\text{ RTT}$，再加上握手、挥手所占用的 RTT 份额。

### 3. 高频大题陷阱与采分防错要点

#### 陷阱 1：序号消耗规则混淆
- **SYN 报文段**：不携带数据，但**必须消耗 1 个序号**。连接建立后首个数据段的起始序号为 $\text{ISN} + 1$。
- **FIN 报文段**：不携带数据，但**必须消耗 1 个序号**。四次挥手 ACK 确认号为 $\text{FIN 的 seq} + 1$。
- **纯 ACK 报文段**：不携带数据，**不消耗任何序号**。下一报文段仍使用该 ACK 报文段相同的序号。

#### 陷阱 2：MSS 与 MTU 的概念界限
- $\text{MTU}$（最大传输单元）作用于数据链路层（以太网标准通常为 $1500\text{ B}$）。
- $\text{MSS}$（最大报文段长度）作用于传输层，仅指 TCP 报文段中的**有效数据载荷最大字节数**，不包含 TCP 首部和 IP 首部。
  $$\text{MSS} = \text{MTU} - \text{IP首部长度} - \text{TCP首部长度}$$
  在无选项字段时，标准首部各为 $20\text{ B}$，此时 $\text{MSS} = 1500 - 20 - 20 = 1460\text{ B}$。大题中若给出 $\text{MSS} = 1000\text{ B}$，则每个段携带的纯数据就是 $1000\text{ B}$，切勿额外扣除 $40\text{ B}$ 首部。

#### 陷阱 3：In-flight 数据的遗漏扣除
选择题和大题设问“当前还能发送多少数据”时，题干往往故意呈现已经发出但尚未确认的段。
**核心公式必须死守**：
$$\text{允许继续发送量} = \min(cwnd, rwnd) - \text{已发送未确认字节量 (In-flight)}$$

## 五、 考点速记清单

### 1. 核心公式与定理速查表

| 物理量名称 | 数学表达式 / 演化规则 | 适用场景与关键说明 |
|:---|:---|:---|
| **发送窗口上限** | $swnd = \min(cwnd, rwnd)$ | 拥塞窗口与通告接收窗口共同约束 |
| **可用发送窗口** | $\text{Usable} = swnd - (P_2 - P_1)$ | $P_2 - P_1$ 为已发送未确认在途数据（In-flight） |
| **发送窗口右边界** | $P_3 = P_1 + swnd = ack\_seq + swnd$ | $P_1$ 为当前已收到的最大累积确认号 |
| **慢开始窗口增长** | 每收到 1 个对新段的 ACK：$cwnd \leftarrow cwnd + 1\text{ MSS}$<br>每经过 1 个 RTT：$cwnd \leftarrow 2 \times cwnd$ | 适用阶段：$cwnd < ssthresh$ |
| **拥塞避免增长** | 每经过 1 个 RTT：$cwnd \leftarrow cwnd + 1\text{ MSS}$ | 适用阶段：$cwnd \ge ssthresh$，线性加法增大 |
| **确认号生成** | $ack\_seq = seq + L$ | $seq$ 为接收段起始序号，$L$ 为其载荷字节数 |
| **数据首字节序号** | $seq_{\text{first}} = \text{ISN} + 1$ | 握手 SYN 消耗 1 个序号 |

### 2. 解题极速判断口诀
- **序号单位找准字节**：报文长度看载荷，首部开销不占序号。
- **确认号看期待值**：累积确认保连续，收到几号前全齐，期待下一个首字节。
- **双重限制取其轻**：$swnd$ 紧盯 $\min(cwnd, rwnd)$，慢开始翻倍增，拥塞避免加一轮。
- **能发多少先减在途**：窗口定额是上限，在途未确需扣除，余量才为可用度。
- **死锁救星持续钟**：零窗一现计时启，超时试探一字节，强制回传破僵局。
